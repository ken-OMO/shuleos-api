## Context

ShuleOS manages files associated with many school and platform workflows, including:

- Learner documents
- Birth certificates
- Assessment documents
- Teacher documents
- National identification references
- TSC-related records
- Passport photographs
- School branding assets
- Lesson resources
- Schemes of work
- Lesson plans
- Lesson notes
- Records of work
- Examination materials
- Report cards
- Receipts
- Payment evidence
- Boarding records
- Transport records
- Communication attachments
- Security evidence
- Audit exports
- Generated reports

These files may contain sensitive learner, guardian, employee, financial, academic, and operational information.

Local application disk storage is not suitable as the long-term production storage architecture because it:

- Couples files to one application instance
- Complicates horizontal scaling
- Creates deployment and replacement risks
- Makes multi-instance access difficult
- Increases backup complexity
- Encourages unsafe public file exposure
- Creates weak separation between temporary, quarantined, and approved files

The platform requires private, durable, scalable, provider-backed object storage with controlled access.

## Decision

ShuleOS will use Cloudflare R2 as the approved production object-storage platform.

R2 will store private tenant-owned and platform-owned objects through ShuleOS-controlled storage services.

Files will not be treated as public merely because they exist in object storage.

All protected access will require server-side authorization and approved temporary access mechanisms.

The architecture will support:

- Private buckets
- Tenant-aware ownership metadata
- Non-guessable object keys
- Signed or controlled temporary access
- Quarantine before permanent availability
- Malware scanning
- File validation
- Retention policies
- Audit logging
- Provider abstraction
- Backup and recovery planning
- Future migration to another S3-compatible provider

## Core Architecture

```text
Client Upload
    |
    v
Authenticated Upload Request
    |
    v
Tenant and Permission Validation
    |
    v
File Metadata Validation
    |
    v
Temporary or Quarantine Storage
    |
    v
Malware and Content Inspection
    |
    v
Approval Decision
    |
    v
Protected R2 Object Storage
    |
    v
Database File Record
    |
    v
Authorized Access through Signed or Controlled URL
```

The database stores file metadata and ownership.

R2 stores the object bytes.

Neither layer is sufficient alone.

## Storage Ownership

Every stored object must belong to one of these scopes:

- Platform
- White-label brand
- School tenant
- Approved user-private scope
- Approved temporary processing scope

Most school files belong to exactly one school tenant.

File ownership must be explicit in the database.

Object-key structure must not be the only source of ownership truth.

## File Metadata Record

Every protected file should have a database record containing approved metadata such as:

- File identifier
- Tenant or platform ownership
- Original filename
- Safe display filename
- Storage disk or provider
- Object key
- MIME type
- Detected MIME type
- Extension
- Size
- Cryptographic hash
- Upload status
- Scan status
- Quarantine status
- Related resource type
- Related resource identifier
- Uploader
- Retention category
- Created time
- Archived time
- Deleted time where applicable

Sensitive provider credentials must never be stored in file metadata.

## Object Keys

Object keys must be non-guessable and generated by the server.

A conceptual structure may be:

```text
schools/{school_uuid}/{category}/{year}/{random_object_id}
```

or:

```text
platform/{category}/{random_object_id}
```

Object keys must not contain unnecessary personal data such as:

- Learner names
- National identification numbers
- Birth certificate numbers
- Phone numbers
- Email addresses
- Admission numbers where avoidable

Human-readable metadata belongs in the database, not in public object paths.

## Private Buckets

Protected ShuleOS files must use private buckets.

Public bucket access is prohibited for sensitive or tenant-owned data.

Public access may be used only for explicitly approved non-sensitive assets, such as:

- Public branding assets
- Public documentation assets
- Public marketing images

Public access requires a documented classification and review.

## Upload Workflow

The approved upload flow is:

```text
Upload request received
    |
    v
Authentication verified
    |
    v
Tenant resolved
    |
    v
Permission and ownership checked
    |
    v
Upload policy resolved
    |
    v
Filename, size, MIME, and extension validated
    |
    v
File stored in temporary quarantine
    |
    v
Hash calculated
    |
    v
Malware and content checks performed
    |
    v
Approved or rejected
    |
    v
Approved file promoted to protected storage
    |
    v
Audit event recorded
```

A file must not become available to ordinary users before required checks complete.

## Optional Documents

Document uploads are optional where the workflow permits.

For learner registration, teacher registration, and similar workflows, ShuleOS may accept verified document numbers without requiring a file upload.

Examples include:

- Birth certificate number
- Assessment number
- National ID number
- TSC number

The system should support:

- Document number available
- File available
- Number only
- File only where legally appropriate
- Not available, recorded as `N/A` where permitted

The absence of a file must not block a workflow unless a documented legal or institutional rule requires it.

## Passport Photographs

ShuleOS may capture and normalize profile photographs to approved passport-style dimensions.

Image processing may include:

- Cropping
- Resizing
- Orientation correction
- Compression
- Format normalization
- Thumbnail generation
- Metadata removal

The original image should not automatically be retained if the normalized version satisfies the business and legal requirement.

Photograph handling must preserve consent, privacy, and access controls.

## Validation

File validation must include:

- Allowed extension
- Declared MIME type
- Detected MIME type
- File signature or magic-byte checks
- Size limits
- Filename normalization
- Character restrictions
- Archive inspection where allowed
- Image dimension limits where relevant
- Content-specific rules

The original client filename must never determine storage location.

## Allowed File Types

Allowed types must be defined per workflow.

Examples may include:

- PDF
- JPEG
- PNG
- WebP
- Approved office-document formats where required

Executable files, scripts, and unsafe archive formats are prohibited by default.

An allowed extension alone is not sufficient proof of file type.

## Size Limits

File-size limits must be defined per category.

Examples:

- Passport photographs
- Identity documents
- Lesson resources
- Examination files
- Report exports
- Bulk imports

Large files should use controlled multipart upload where justified.

Size limits must protect platform cost and performance.

## Quarantine

New files enter quarantine by default when scanning or validation is required.

Quarantined objects:

- Are not available through ordinary download routes
- Cannot be attached to published resources
- Cannot be shared externally
- Have restricted operational access
- Are deleted or archived after rejection according to policy

Quarantine status must be stored explicitly.

## Malware Scanning

Files must be scanned before permanent availability where the threat model requires it.

Scanning may include:

- Malware detection
- Suspicious archive detection
- Embedded-script detection
- Document macro checks
- Image-parser safety checks
- Content-disarm and reconstruction in future

A scanner timeout must not be treated as successful scanning.

Approved statuses may include:

- Pending
- Clean
- Suspicious
- Infected
- Scan Failed
- Rejected

## File Hashing

A cryptographic hash should be calculated for stored objects.

Hashes support:

- Integrity verification
- Duplicate detection
- Evidence preservation
- Upload verification
- Migration validation

Hashing must not be treated as malware scanning.

## Direct Uploads

Clients may use pre-signed upload URLs where appropriate.

Before issuing a pre-signed upload URL, the server must validate:

- Identity
- Tenant
- Permission
- Upload category
- Maximum size
- Expected content type
- Expiry
- Object-key ownership

A successful direct upload does not automatically make the file approved.

The client must complete an upload-finalization step, after which the server verifies the object and begins scanning.

## Download Access

Protected downloads must require current authorization.

A download flow may use:

- Server-streamed response
- Short-lived signed URL
- Controlled proxy endpoint
- One-time access token where justified

Before granting access, the server must revalidate:

- Identity
- Tenant
- Permission
- Resource ownership
- File state
- Retention state
- Related-resource state

Possession of an old signed URL must not grant indefinite access.

## Signed URLs

Signed URLs must be:

- Short-lived
- Scoped to one object
- Generated only after authorization
- HTTPS-only
- Non-transferable where practical
- Audited for sensitive files
- Invalidated through short expiry rather than assumed revocation

Sensitive filenames should not appear unnecessarily in signed URLs.

## File Status

Approved file lifecycle states may include:

- Pending Upload
- Uploaded
- Quarantined
- Scanning
- Clean
- Approved
- Rejected
- Archived
- Retention Hold
- Pending Deletion
- Deleted
- Lost or Missing
- Migration Required

State transitions must be validated and audited.

## Attachment Relationships

A file may be linked to one or more approved resources.

Examples include:

- Learner
- Teacher
- Payment
- Invoice
- Lesson note
- Examination
- Communication
- Support case

Attachment relationships must verify that both the file and resource belong to the same authorized scope.

Cross-tenant attachment is prohibited.

## Tenant Isolation

Tenant isolation applies to:

- Upload initiation
- Object keys
- Metadata
- Scanning
- Attachment relationships
- Download authorization
- Signed URLs
- Retention
- Deletion
- Migration
- Audit logs

A school must never access another school's object even if it obtains the object key.

## Platform Files

Platform-owned files include:

- Subscription invoices
- Platform receipts
- Platform security evidence
- Platform documentation
- Platform support artifacts

Platform files must use platform permissions and must not be exposed through school-level file APIs unless explicitly authorized.

## Brand-Level Files

Brand-level files may be shared with explicitly governed schools.

Brand sharing must:

- Use approved brand scope
- Define intended schools
- Avoid implicit global availability
- Be audited
- Preserve current access checks

## Encryption

R2 transport must use TLS.

Provider-side encryption must be enabled or relied upon according to the approved R2 service model.

Highly sensitive categories may require additional application-level encryption.

Application-level encryption requires:

- Key management
- Rotation
- Recovery planning
- Access controls
- Performance review
- A dedicated design or ADR where necessary

Encryption does not replace authorization.

## Credential Management

R2 credentials must be:

- Stored outside source control
- Environment-specific
- Rotatable
- Least-privileged
- Restricted to required buckets and operations
- Redacted from logs
- Excluded from API responses
- Audited when changed

Production and development credentials must be separate.

## Provider Abstraction

ShuleOS must access R2 through an approved storage abstraction compatible with S3-style object storage.

Business domains must not depend directly on Cloudflare-specific SDK behaviour.

The abstraction should support:

- Upload
- Download
- Signed URL
- Delete or archive
- Metadata lookup
- Copy or move
- Integrity verification
- Provider migration

This preserves provider replaceability.

## Local Development

Local development may use:

- Laravel local storage
- S3-compatible local emulators
- Approved test doubles
- Dedicated development R2 buckets

Development storage must preserve the same logical access rules.

Tests must not pass merely because local disk bypasses production authorization.

## Migration from Local Storage

Existing local files must be inventoried before migration.

Migration should:

1. Enumerate file records.
2. Verify tenant ownership.
3. Calculate hashes.
4. Upload to R2.
5. Verify object integrity.
6. Update metadata transactionally or through controlled batches.
7. Preserve audit evidence.
8. Retain rollback capability.
9. Remove local copies only after verification.

Missing or orphaned files must be reported.

## Data Residency

The selected R2 storage and processing configuration must be documented for legal and compliance review.

The architecture must record:

- Applicable storage location model
- Cross-border transfer considerations
- Backup or replication behaviour
- Provider subprocessors
- Contractual safeguards
- Children's data implications

Data residency decisions must not be assumed.

## Retention

Every file category must have a retention policy.

Retention may depend on:

- Legal requirement
- School policy
- Contractual requirement
- Academic lifecycle
- Financial lifecycle
- User request
- Security evidence
- Child-data minimization

Files must not be retained forever by default.

## Retention Holds

A retention hold may prevent deletion because of:

- Legal dispute
- Audit
- Security investigation
- Financial reconciliation
- Regulatory requirement

Retention holds require elevated permission and audit logging.

## Archiving

Archive-first rules apply to file records.

Archiving should:

- Preserve ownership
- Restrict ordinary access
- Preserve audit history
- Retain metadata
- Avoid public exposure
- Support approved restoration

Archived files may move to a lower-cost storage class if supported and reviewed.

## Deletion

Deletion must be deliberate.

The process may include:

- Archive
- Retention review
- Deletion approval
- Object deletion
- Metadata tombstone
- Audit event
- Backup lifecycle expiry

A database record must not be deleted while the object remains unmanaged.

An object must not be deleted while an active file record still promises availability.

## Orphan Detection

The platform must detect:

- Database record without object
- Object without database record
- Attachment without file
- File with invalid tenant
- File with failed scan but approved status
- Expired temporary object
- Abandoned multipart upload

Orphan reconciliation should run through controlled scheduled jobs.

## Backup and Recovery

R2 is not automatically a complete backup strategy.

ShuleOS must document:

- Object-versioning behaviour where available
- Backup exports where required
- Metadata backup
- Recovery procedure
- Accidental deletion response
- Provider outage response
- Credential-loss response
- Provider migration procedure

Restore testing must verify that file metadata and object bytes can be reconnected correctly.

## Integrity Verification

Periodic integrity checks may compare:

- Stored hash
- Object size
- Provider metadata
- Database metadata
- Attachment ownership

Integrity failures must generate alerts and investigation records.

## Availability

The platform must handle temporary R2 unavailability safely.

Possible behaviour includes:

- Retry
- Queue deferred uploads
- Temporary unavailable response
- Prevent publication until upload completes
- Alert operations
- Preserve local temporary file only within approved limits

The system must not claim a file is available when storage confirmation failed.

## File Processing Jobs

Image conversion, document preview, OCR, thumbnailing, and scanning should run asynchronously where practical.

Jobs must:

- Preserve tenant context
- Be idempotent
- Use bounded retries
- Clear temporary files
- Record status
- Avoid exposing files through temporary public paths

## Generated Files

Generated exports and reports must use the same security model as uploaded files.

Generated files must include:

- Tenant ownership
- Expiry where appropriate
- Authorized download
- Retention category
- Audit logging
- Cleanup scheduling

## Caching and CDN

A CDN may accelerate approved file delivery.

Caching must not turn protected files into public content.

For private assets:

- Cache keys must avoid tenant collision
- Signed access must remain short-lived
- Cache-control headers must reflect sensitivity
- Revocation expectations must be documented

Public assets require separate classification.

## Logging

Logs must not contain:

- R2 secret keys
- Signed URL signatures
- Raw private URLs
- Full sensitive filenames where unnecessary
- Personal document numbers
- File contents

Safe logs may contain:

- File identifier
- Tenant identifier
- Category
- Size
- Status
- Correlation identifier
- Safe provider error code

## Audit Logging

Sensitive file events should include:

- Upload initiated
- Upload completed
- Scan result
- Approval
- Rejection
- Download authorization
- Signed URL issued
- Attachment created
- Attachment removed
- Archive
- Restore
- Retention hold
- Deletion
- Provider migration
- Integrity failure

## Observability

Metrics should include:

- Upload volume
- Download volume
- Storage usage
- Per-tenant storage usage
- Quarantine queue depth
- Scan latency
- Scan failure rate
- Rejected-file count
- Signed URL issuance
- Missing-object count
- Orphan count
- Migration failures
- Provider latency
- Provider errors
- Cost estimates

Critical anomalies must generate alerts.

## Noisy-Neighbour Protection

One school must not consume uncontrolled storage or processing resources.

Controls may include:

- Per-tenant quotas
- File-size limits
- Daily upload limits
- Concurrent upload limits
- Scan queue fairness
- Export limits
- Processing budgets
- Storage usage alerts

Quota enforcement must not expose another tenant's usage.

## Privacy

File storage must follow data-minimization principles.

The platform should avoid retaining:

- Duplicate uploads
- Unnecessary originals
- Excess metadata
- Embedded geolocation
- Unneeded document properties
- Temporary processing copies

Learner files receive the highest privacy classification.

## Child Data Protection

Documents involving learners require stricter controls.

Examples include:

- Birth certificates
- Health documents
- Assessment records
- Passport photographs
- Guardian documents

Access must be limited to roles with a documented educational, administrative, or legal need.

## Examination Confidentiality

Unpublished examination materials require restricted access.

Controls may include:

- Publication-state checks
- Time-based access
- Role restrictions
- Download auditing
- Watermarking where appropriate
- No public links
- Strong retention and release rules

## Security Incident Response

Events such as the following are security incidents:

- Public exposure of a private bucket
- Cross-tenant file access
- Credential compromise
- Malware delivered to users
- Missing learner documents
- Unauthorized bulk download
- Signed URL abuse
- Storage integrity failure

Incident response must preserve evidence and support credential rotation.

## Alternatives Considered

### Local Disk Storage in Production

Rejected.

It does not support reliable horizontal scaling and creates operational risk.

### Public Object Storage

Rejected for protected files.

Public access is incompatible with ShuleOS privacy and tenant requirements.

### Database Binary Storage

Rejected as the default.

Storing large objects directly in PostgreSQL would increase database size, backup cost, and query operational burden.

### Cloudflare R2

Accepted.

R2 provides S3-compatible object storage, scalable capacity, and integration flexibility while supporting provider abstraction.

## Consequences

### Positive

- Supports horizontal application scaling
- Separates file bytes from application instances
- Enables private protected access
- Supports signed URLs
- Improves storage durability
- Supports provider abstraction
- Enables tenant quotas and usage tracking
- Supports asynchronous processing
- Simplifies future CDN use

### Negative

- Introduces an external provider dependency
- Requires credential and bucket management
- Upload and download failures become distributed-system concerns
- Signed URL security requires careful implementation
- Malware scanning requires additional infrastructure
- Backup and residency responsibilities remain with ShuleOS
- Migration from local files requires careful verification

These costs are accepted because production-grade file storage is a core platform requirement.

### Risk: Cross-Tenant File Access

Mitigation:

- Database ownership records
- Server-side authorization
- Short-lived signed URLs
- Tenant-aware attachment checks
- Cross-tenant tests

### Risk: Public Bucket Misconfiguration

Mitigation:

- Private-by-default infrastructure
- Configuration review
- Automated policy checks
- Monitoring
- Incident response

### Risk: Malicious Upload

Mitigation:

- Quarantine
- MIME and signature validation
- Malware scanning
- File-type allowlists
- Size limits

### Risk: Credential Leakage

Mitigation:

- Secret storage
- Least privilege
- Rotation
- Environment separation
- No logging

### Risk: Object Missing but Metadata Exists

Mitigation:

- Integrity checks

Mitigation:

- S3-compatible abstraction
- Provider-neutral metadata
- Migration tools
- No domain dependency on provider SDKs

## Final Decision

ShuleOS will use Cloudflare R2 as its approved production object-storage platform.

All protected files will remain private, tenant-aware, validated, scanned, auditable, and accessible only through current authorization and approved temporary-access mechanisms.

R2 will be accessed through a provider abstraction so that storage remains replaceable and domain logic does not depend directly on Cloudflare-specific implementation details.
